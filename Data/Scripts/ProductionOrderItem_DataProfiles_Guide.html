جزئیات POI_All_ReadyForShipping (Id=123)

WHERE
    [t1].[IsDeleted] = 0
    AND [t1].[IsLatestVersion] = 1
    AND [t1].[Status] = 579                       -- NotCompleted (وضعیت 0 در HTS)
    AND NOT EXISTS (                              -- هیچ قلم هم‌سفارشِ ناتمامِ غیر-آماده‌ای نباشد
        SELECT 1 FROM [Sale].[ProductionOrderItem] AS [sib]
        WHERE [sib].[ProductionOrderId] = [t1].[ProductionOrderId]
          AND [sib].[IsDeleted] = 0
          AND [sib].[IsLatestVersion] = 1
          AND [sib].[Status] = 579
          AND [sib].[ProductionStep] <> 221        -- ReadyForShipping
    )

تست روی داده واقعی: از ۱۲۴ قلم با Status=579 AND ProductionStep=221، فقط ۱۶ قلم این شرط را برآورده می‌کنند (یعنی متعلق به سفارش‌هایی هستند که تمام اقلام ناتمام‌شان آماده ارسال است). این تفاوت (۱۲۴ در برابر ۱۶) دقیقاً همان چیزی است که فرمول HTS با GroupBy + Items.Count(ready) == Items.Count هدفش بود.

چرا Query دستی به‌جای Filter Builder؟

بررسی کد نشان داد وقتی QueryDesign.CustomQuery پر باشد، QueryService (در هر دو مسیر Preview و رندر DataTable) مستقیماً همان متن را اجرا می‌کند و لیست Filters اصلاً به WHERE تبدیل نمی‌شود؛ بنابراین منطق شرطی پیچیده (OR بین چند Role) فقط با نوشتن WHERE داخل خودِ CustomQuery ممکن است.

متغیرهای واقعاً در دسترس داخل Query

ParameterResolverService فقط دو مقدار کاربر جاری را واقعاً Resolve می‌کند: @CurrentUserId و @CurrentUserName. مقادیر @CurrentUserRole(s) و @CurrentUserOrganizationId/Name در کد فعلی صرفاً Placeholder هستند و همیشه NULL برمی‌گردانند (پیاده‌سازی نشده‌اند). به همین دلیل، Role/واحد سازمانی کاربر جاری با یک Join به system.[User] روی @CurrentUserId و خواندن ستون‌های RoleIds/Roles (آرایه JSON) با OPENJSON استخراج می‌شود؛ نه از پارامترهای از‌پیش‌تعریف‌شده. 

DECLARE @CuId BIGINT = TRY_CAST(@CurrentUserId AS BIGINT);
DECLARE @CuRoles NVARCHAR(MAX), @CuRoleIds NVARCHAR(MAX);
SELECT @CuRoles = Roles, @CuRoleIds = RoleIds FROM system.[User] WHERE Id = @CuId;

DECLARE @HasIndustrial BIT = CASE WHEN EXISTS (
    SELECT 1 FROM OPENJSON(@CuRoleIds) WHERE TRY_CAST([value] AS BIGINT) = 200023
) THEN 1 ELSE 0 END;
-- ... به همین شکل برای بقیه نقش‌ها ...
--!--mainsection   <-- Marker داخلی DatabaseSchemaService؛ جدا می‌کند بخش DECLARE را از SELECT
SELECT ... FROM Sale.ProductionOrderItem t1 LEFT JOIN Sale.ProductionOrder t2 ON ... WHERE (...)

Marker --!--mainsection برای این لازم است که در رندر صفحه‌بندی‌شده، DatabaseSchemaService.ExecuteQueryWithPaginationAsync عبارت SELECT را داخل SELECT * FROM (...) AS [__t] می‌پیچد؛ DECLARE نمی‌تواند داخل این زیرکوئری باشد، پس باید قبل از Marker (خارج از پرانتز) بماند.

نکات طراحی مهم (تصمیم‌های عمدی)

  • چرا ProductionStep IN (0, 2744) برای صنایع؟ چون AcceptIndustrial هیچ‌وقت CheckStatus را عوض نمی‌کند (فقط ProductionStep را به ۲۱۴ می‌برد)، دیتای واقعی نشان داد ۲٬۴۴۰ قلم با CheckStatus=1904 سال‌ها پیش تحویل‌شده‌اند (ProductionStep=223) و فقط ۱۰۰ قلم واقعاً دست‌نخورده‌اند (۰ یا ۲۷۴۴). بدون این شرط، کارتابل صنایع نمایش هزاران رکورد بی‌ربط می‌داد.
  • چرا مدیر پروژه هم با Role هم با شناسه؟ چون فعلاً هیچ کاربری Role مربوطه (200026) را ندارد؛ افزودن ProjectManagerId = شناسه کاربر جاری باعث می‌شود مدیر پروژه واقعیِ سفارش (بدون نیاز به انتساب Role) نیز قلم خودش را ببیند — همان «شناسه شخص جاری» که در درخواست اشاره شد.
  • «واحد سازمانی» (OrgUnit) عمداً در فیلتر استفاده نشد؛ چون در کد فعلی (ProductionOrderItemController) هیچ مجوزی بر مبنای OrgUnit بررسی نمی‌شود (برخلاف HTS که OrgUnit ۱۷/۱۴۳/۳۰ Hardcode بود). افزودن آن بدون پشتوانه در Authorization واقعی، ریسک نمایش/عدم‌نمایش نادرست ایجاد می‌کرد.
  • Sale.ProductionOrder.Obsolete عمداً شاخه‌ای در این کارتابل ندارد؛ چون یک صف «منتظر اقدام» با CheckStatus مشخص نیست، بلکه یک مجوز همیشه-در-دسترس است.

به‌روزرسانی: مسیریابی مهندسی بر اساس Pln.ProductionOrderEquipmentConfirmer

پس از اصلاح جدول Pln.ProductionOrderEquipmentConfirmer (به‌ازای هر DeviceType، یک تاییدکننده مکانیک و یک تاییدکننده برق مشخص)، شاخه‌های مهندسی مکانیک/برق در POI_MyCartable اصلاح شدند تا به‌جای نمایش همه اقلام به هر کسی که Role عمومی AcceptEngineeringMechanical/AcceptEngineeringElectrical دارد، فقط اقلامی را نشان دهند که خودِ همان کاربر به‌عنوان تاییدکننده همان DeviceType در جدول تنظیمات ثبت شده است. 

-- شاخه مهندسی مکانیک (شاخه برق مشابه با ElectricalUserId)
[t1].[CheckStatus] = 2195
AND ([t1].[DeviceType] IS NULL OR [t1].[DeviceType] NOT IN (2403,2404,2212,2211))
AND (
    @HasShowAll = 1
    OR EXISTS ( -- کاربر جاری تاییدکننده اختصاصی همین DeviceType است
        SELECT 1 FROM [Pln].[ProductionOrderEquipmentConfirmer] pec
        WHERE pec.[DeviceType] = [t1].[DeviceType] AND pec.[MechanicalUserId] = @CuId
    )
    OR ( -- fallback: اگر برای این DeviceType هیچ تاییدکننده معتبری تعریف نشده، نقش عمومی کافی است
        @HasEngMech = 1
        AND NOT EXISTS (
            SELECT 1 FROM [Pln].[ProductionOrderEquipmentConfirmer] pec2
            WHERE pec2.[DeviceType] = [t1].[DeviceType] AND pec2.[MechanicalUserId] IS NOT NULL
        )
    )
)

Fallback عمداً اضافه شد چون برخی DeviceType ها (مثل ۲۴۵۵/نامشخص یا ۲۴۰۶ که کاربر تاییدکننده‌اش هنوز در هوایار حساب ندارد) بدون تاییدکننده معتبر هستند؛ بدون Fallback این اقلام برای هیچ‌کس (جز ShowAll) دیده نمی‌شدند. تست شد: Saeedi.m (تاییدکننده مکانیک ۹ نوع دستگاه) فقط ۱۱۰۳ قلم مربوط به همان ۹ نوع را می‌بیند؛ کاربر بدون تخصیص شخصی فقط ۳۵ قلم Fallback (نوع‌های بدون تاییدکننده معتبر) را می‌بیند.
